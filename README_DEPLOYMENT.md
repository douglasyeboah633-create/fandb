
## 11. Backup and restore

Settings → Backup provides JSON/CSV **record exports**, not full disaster-recovery backups. Exports omit uploaded file contents and authentication data and have no built-in import/restore command.

For SQLite, stop all application processes and background writers before copying `C:\Users\MacBook Pro\Desktop\land\db.sqlite3` and the entire `C:\Users\MacBook Pro\Desktop\land\media` directory to a dated, encrypted backup location. Keep a secure copy of `.env`, the application version and dependency pins. Restrict backup access because records contain personal and financial information. Use PostgreSQL-native backup tools for PostgreSQL.

To restore: stop the application; preserve the current database and media as a rollback copy; restore the matching database and media backup together into their original paths; restore the compatible application/configuration; run `manage.py migrate` only after checking version compatibility; then run `manage.py check` and verify customer counts, balances and document downloads in an isolated environment before reopening access. Test recovery regularly. A successful file copy alone does not establish recoverability.

## 12. Deployment and verification

Before deployment, resolve the release limitations below and obtain an application/security review. On a supported production host:

- Install pinned dependencies in an isolated environment and use a supported production WSGI/ASGI server. `landpro.wsgi:application` is the WSGI entry point. The optional Gunicorn dependency in requirements is for Linux; it is not installed or tested here.
- Set a unique `DJANGO_SECRET_KEY`, `DJANGO_DEBUG=False`, exact `DJANGO_ALLOWED_HOSTS`, and HTTPS `DJANGO_CSRF_TRUSTED_ORIGINS` in the deployment environment.
- Terminate HTTPS at a trusted reverse proxy. It must overwrite `X-Forwarded-Proto`, not forward an arbitrary client value. Review HSTS/subdomain settings before enabling them for a real domain.
- Do not expose `db.sqlite3`, `.env`, backups, logs or `media` through public web-server aliases. Documents are served through authenticated application downloads; there is deliberately no public development media route.
- Run migrations, collect static files and run deployment checks using the production environment. Serve collected assets with WhiteNoise. Provision persistent private media storage, backups, log rotation and monitoring.
- Configure a production email backend in `MAILERS` before release. The current console backend is development-only and `check --deploy` reports `mail.E001`; email delivery has not been implemented or tested for deployment.
- Remove demo accounts/data, rotate secrets, apply least privilege, and test restore, TLS, authorization and expected concurrent load before launch.

Collect static files before tests: the public-route smoke test intentionally uses manifest-backed storage. Tests use an isolated temporary database and temporary upload directory, not the demo database. The suite checks all view-referenced templates, authenticated list/detail/edit pages, report formats, receipt PDF generation, role restrictions, CSRF, error pages, document upload/download/deletion, payment arithmetic, overpayment defaults, plot reassignment and payment preselection.

### Release limitations / remaining work

- Concurrent financial writes are not yet protected by a complete transaction/locking strategy. Sequential display IDs are generated by scanning existing records and can collide under concurrent inserts; database uniqueness prevents duplicates but can surface errors. Sale creation plus initial payment and audit writes need atomic handling, retries and concurrent integration tests before multi-user production use.
- Financial records are editable/deletable, not an immutable accounting ledger. Audit entries originate in application views and do not cover every possible ORM/admin/database change. Define retention, reversal, approval and tamper-resistance requirements before financial compliance use.
- Payment/sale edits, especially reassignment or reducing a price below prior payments, require further business-rule review. Overpaid sales clamp displayed outstanding to zero; aggregate reports may show a net credit. Historical receipts are not frozen snapshots.
- All authenticated staff can view business records and reports; there is no tenant/customer-level isolation. Rate limiting/MFA, file malware inspection, export sanitization and comprehensive adversarial security review remain deployment work.
- Automated tests validate HTML rendering and PDF/Excel signatures, not visual print fidelity. Responsive CSS includes 1100/800/450 px breakpoints, collapsible navigation and horizontally scrollable tables; actual desktop/mobile browser, keyboard and screen-reader acceptance testing remains required.
- Production hosting, PostgreSQL, high-volume performance and backup restoration have not been exercised here. Passing local tests is not a production-readiness certification.
